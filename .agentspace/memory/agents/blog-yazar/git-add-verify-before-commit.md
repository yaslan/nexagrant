Running `git add <my-file-only> && git commit` is NOT safe in this repo, even though `git add` only stages the path given. Between the `add` and the `commit`, another agent's own `git add` (on their unrelated files, in the same shared working tree/index) can land in the index first — and `git commit` with no pathspec commits the *whole* index, not just what I just added.

**Why:** Concrete incident (TASK-MTQU0SAD85B8X, 2026-09-07): staged only my own result-report markdown file, then committed. `blok-zincir-dse`'s in-progress G0-production-wiring work (TASK-MTQ63RR8Z0G8E — `g0-compute.ts`, `g0-features.ts`, `evaluate.ts`, scratch `qd.mjs`/`qd2.mjs`, screenshots — 16 files) was staged in the shared index at that moment and got swept into my commit under my unrelated commit message. Content turned out to be real, finished, non-broken work (typecheck came back clean on a re-run — the first failure was a transient race from a third agent editing a file live, not a regression), so no damage was done, but the commit is misattributed and could have confused the owning agent's own commit flow. This is the concrete case behind [[fabrika-parallel-agent-file-race]] — that memory names the risk, this one is the worked example of how easily it happens even when you think you scoped `git add` correctly.

**How to apply:** In this repo, before *every* commit — not just ones with `git add -A` or `.` — run `git diff --cached --name-only` (or `--stat`) immediately before `git commit` and confirm the list is exactly what you intended, even if you just ran a scoped `git add <path>`. If it isn't, `git restore --staged <unwanted paths>` before committing rather than committing everything and sorting it out after. Do not "fix" an already-landed sweep-in with `reset`/`revert` — that risks destroying another agent's real work; instead document it transparently (as done here) and let the owning agent/PM confirm.

**`git stash` / `git stash pop` re-triggers the same risk, even for a read-only check.** TASK-MTRHADHCV9W7A (2026-09-07): needed to prove a `pnpm typecheck` failure predated my change, so I ran `git stash` (stashed everyone's uncommitted work, including mine), typechecked the clean base commit, then `git stash pop` to restore. The pop brought back not just working-tree edits but the *staged index other agents had before the stash* — so a plain `git add <my-file> && git commit` right after a stash pop staged a dozen unrelated agents' files (`plan-repository.ts`, several other agents' result reports, memory files) alongside mine. Caught it with the same `git diff --cached --name-only` check and `git restore --staged`'d everything but my own path before committing. No stash/pop-based read-only check is actually side-effect-free here — always re-run the cached-name-only check right after the pop, not just after your own `git add`.

**The sweep isn't always an addition — it can be a DELETION, and `git status --porcelain -- <my paths>` hides it.** TASK-MTSJKTGDUC3L5 (2026-09-08): added a new `docs/agent-results/…` protection block to `githooks/pre-commit`, plus a result-report file. Checked `git status --porcelain -- githooks/pre-commit docs/agent-results/TASK-….md` (pathspec-filtered) right before committing — clean, only my two files. Committed with plain `git add <2 paths> && git commit` (no commit-time pathspec). The commit landed with **4 files, not 2**: another agent's in-progress refactor (moving off `src/types/prisma-override.d.ts` to generated Prisma types) had `git rm`'d that file and its test, staged, uncommitted, at that exact moment — my plain `git commit` wrote the *whole* index, including their deletion, under my commit message. Their own remaining changes (`src/lib/db.ts`, `billing.ts`, `k2-cordis/importer.ts`, `schema-contract.test.ts`) were still sitting unstaged, so the result was a **half-finished foreign refactor published to dev under my commit** — the file the rest of their edits depended on was now gone from HEAD. Root cause of missing this: filtering `git status`/`git diff --cached` **by my own pathspec** only proves my paths are correct, it says nothing about what else is staged. Fixed immediately: restored both files byte-for-byte from the parent commit (`git show <parent>:<path> > <path>`), then committed with the **pathspec form** (`git add <2 paths>` then `git commit -m "…" -- <2 paths>`), and verified `git diff <parent> -- <2 paths>` was empty (exact restore) and `git show --stat` on that commit listed only those 2 files.

**How to apply, refined:** the unfiltered check is the one that matters — `git status --porcelain` with **no pathspec** right before `git commit`, not `git status -- <my files>`. A path-filtered status/diff only confirms your own files are fine; it actively hides a stranger's staged add/delete elsewhere in the shared index, which is exactly what a plain (no-pathspec) `git commit` will still pick up. If a sweep-in already landed and it's a **deletion** (not an addition — see line 13's "do not reset/revert" for the addition case), the safe fix is the opposite of that advice: restore the deleted file's exact prior content (`git show <parent-sha>:<path> > <path>`) and commit *that* — you are not destroying the other agent's work, you're putting back the one file their still-unstaged, still-in-progress changes depend on existing.

**`git diff --cached` being clean is NOT enough if you then run `git commit -- <paths>` (pathspec form).** TASK-MTS80LZI1GRWT (2026-09-08): a shared file (`messages/tr.json`) had contamination sitting *on disk* (another agent's legit but uncommitted `m10`/`repeatLabel` keys, written straight to the file, never staged). I hand-crafted a clean index with `git apply --cached` (only touches the index, not the working tree) and confirmed `git diff --cached` showed only my one-line change. Then `git commit -m "…" -- messages/tr.json messages/en.json …` — and the pathspec form of `git commit` **commits the current working-tree content of the named paths, ignoring what's staged for them.** It grabbed the still-contaminated on-disk file, not my clean index, and the contamination landed in my commit anyway despite the "clean" verification. The fix that actually works is in [[fabrika-commit-with-a-throwaway-index]] (a `GIT_INDEX_FILE` scratch index, never `git commit -- <paths>` on a file someone else is mid-editing on disk). See also [[fabrika-amend-can-hijack-a-later-commit]] for what happened next when I tried to "fix" the resulting commit with `--amend`.
